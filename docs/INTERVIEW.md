# LumenWatch: показать и объяснить

## Показ за две минуты
Добавить контролируемый URL → baseline → изменить текст страницы → повторить проверку → diff/история → искусственный сбой → восстановление. Использовать localhost и вымышленные данные.

## Вопросы и ответы
1. **Что делает проект?** Снимает содержимое страниц, сравнивает с предыдущим снимком, хранит историю и показывает изменения через FastAPI/UI/MCP.
2. **Где основной поток?** main.py/MCP → service.py → probes.py → diff_engine.py → database.py. Один service используется обоими интерфейсами.
3. **HTTP или браузер?** HTTP дешевле и подходит статическим страницам; Playwright нужен для JS. Браузер включается отдельно, сетевые запросы не подменяются LLM.
4. **Как определяется изменение?** Нормализация текста, хеш и детерминированное сравнение. Severity — эвристика, не гарантия бизнес-важности.
5. **Что при сбое?** ProbeError становится понятной ошибкой API; успешная история остаётся. Планировщик продолжает другие цели. Тест имитирует baseline → изменение → отказ → восстановление.
6. **Как хранится история?** SQLite targets/snapshots, внешние ключи; снимки содержат хеш, текст, время и результат сравнения. API ограничивает длину выдачи.
7. **Какая найденная ошибка была полезной?** Контекст sqlite3.Connection коммитит/откатывает, но не закрывает соединение. _connect теперь закрывает его в finally; тест проверяет закрытие и откат ошибочной записи.
8. **Как проверял резервную копию?** Стандартный SQLite backup в временный файл, integrity_check, foreign_key_check и сравнение целей/истории. Исходная рабочая база не затрагивается.
9. **Как тестировал без людей?** FakeProbe/контролируемая страница, отдельные временные БД, ошибки scheduler, HTML-экранирование. Локальные ASGI-замеры не выдаются за реальные посещения.
10. **Что нужно до публичного запуска?** Аутентификация, запрет внутренних адресов и проверка каждого редиректа, сетевые ограничения, квоты, мониторинг и автоматические копии. Текущая модель рассчитана на доверенный локальный запуск.
